Project

AIMS Python Autograder

Automated assessment for notebook-based Python programming tutorials

In development AIMS Rwanda · 2026

The Problem

Python programming tutorials at AIMS Rwanda are assessed through Jupyter notebook submissions. Grading these by hand doesn't scale well: it's slow, it's easy for standards to drift slightly from one submission (or one grader) to the next, and it's hard to reproduce a grade or revisit how it was reached once the tutorial has moved on. As the tutorials continue, that gap between how much grading is needed and how much time there is to do it carefully keeps growing.

The System

The autograder is a Python-based system for automatically assessing programming assignments submitted as Jupyter notebooks. It was built specifically for the AIMS Rwanda preparatory programming tutorials, where students submit notebook-based assignments through Google Classroom.

The system separates submission handling from assessment. Student notebooks are first identified and validated using the assignment's naming convention. A submitted notebook is then converted into a Python module, which is executed against a collection of assignment-specific tests. Each test is associated with a predefined mark in a JSON rubric, allowing the system to calculate an objective score automatically.

This design makes the tests independent of individual submissions: the same assessment logic is applied consistently to every student's notebook, while the marking scheme remains configurable for each assignment.

What It Does

The autograder handles the objective portion of the assessment automatically, while the final review remains instructor-led. This hybrid approach is intended to reduce the repetitive work of marking without treating automated tests as a substitute for human judgement.

  • Validates and identifies student submissions using a defined filename convention.
  • Accepts Jupyter notebooks directly and converts them internally into executable Python modules.
  • Runs assignment-specific pytest test suites against each submission.
  • Associates individual test outcomes with predefined marks and calculates the automated component of the student's score.
  • Produces test-level results that can be reviewed when a submission passes or fails particular parts of an assignment.
  • Leaves qualitative and integrity-related assessment to the instructor, including review of code quality, plagiarism or suspicious similarity, and potential use of prohibited AI tools.

After automated marking, submissions are manually reviewed before grades are finalized. This provides a second layer of assessment for aspects of programming work that are difficult to capture reliably through predefined tests alone.

Architecture

The system is organized around a small set of independent components, each responsible for a different stage of the marking workflow.

  • Submission Manager: identifies valid notebook submissions, extracts the student's identifier from the filename, and associates each submission with its assignment.
  • Notebook Conversion: submitted Jupyter notebooks are parsed with nbformat and converted into Python source using nbconvert.
  • Test Engine: runs the assignment-specific pytest test suite against the converted submission.
  • Marking Configuration: each test is mapped to a predefined number of marks through an assignment-specific marks.json file.
  • Result Collection: pytest output is parsed to determine which tests passed, associate them with their allocated marks, and calculate the student's objective score.

Assignments are therefore kept separate from the core grading engine: adding a new assignment primarily involves defining its tests and marking scheme rather than rewriting the autograder itself.

Design Decisions

A central design decision was to work directly with Jupyter notebooks. The tutorials are notebook-based, so requiring students to submit Python scripts purely for the convenience of the grading system would have added an unnecessary step to their workflow. Instead, notebooks are converted internally before testing.

The assessment logic is separated from the submission itself. Tests live in assignment-specific directories, while the marks allocated to those tests are stored separately in JSON. This means that the weighting of an assignment can be changed without modifying the underlying test logic.

The system also uses multiple tests for individual questions rather than relying on a single test per question. This makes it possible to check normal cases as well as selected edge cases, while allowing partial objective credit within a question.

Execution takes place in a temporary runtime directory. The student's converted submission is created there and the test suite is executed as a separate Python process. This keeps the runtime artifacts for one marking operation separate from the original submission and from other marking runs.

Finally, the system is deliberately assignment-driven rather than hard-coded around a single assignment. The same test engine can load different test suites and marking configurations using an assignment code, allowing new assignments to be added without changing the core grading workflow.

Because the system is being developed alongside the tutorials, real student submissions have become an important source of edge cases. Failures in the marking pipeline are therefore treated as feedback about both the student's submission and the assumptions built into the grading system.

Current Status

The core automated marking pipeline is operational and is being used during the 2026 AIMS Rwanda preparatory programming tutorials. The system can identify submissions, convert notebooks, execute assignment-specific pytest suites, associate test outcomes with predefined marks, and calculate objective scores.

Development is ongoing. The current implementation focuses on the reliable automation of objectively testable programming questions, while more advanced components such as richer feedback generation, plagiarism analysis, and broader grading analytics remain future work.
